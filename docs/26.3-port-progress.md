# Minecraft 26.3 port: progress

Branch `26.3`, started from `2b1d3546` (unchanged 1.21.1 / 6.0.6 sources).
Plan: "Immersive Portals 26.3 Port Plan" artifact. This file records what actually happened.

## Current phase

* The whole tree, including the client, compiles against 26.3 and `./gradlew build` passes.
* Server side runtime: Fabric's headless GameTest server (`./gradlew runGametest`) starts with
  Immersive Portals, DimLib and all registered mixins, creates and loads a world, runs 13
  game tests (teleport validation, cross-dimension teleport, portal save/load) and shuts down.
* Phases 2/3: the mounted-player bypass is fixed and covered by unit and game tests.
* Client runtime (phase 4): a client gametest (`./gradlew runClientGametest`) drives the real
  client in a singleplayer world on **OpenGL and on Vulkan**: the nether is loaded as a second
  client world through a portal, walking through the portal changes dimension seamlessly on
  client and server, chunks render in the new dimension, a vanilla cross-dimension `/tp` works
  with several client worlds, and leaving the world cleans up the client worlds.
* Phase 5 (rendering feasibility, amendment 3): a render-to-texture prototype
  (`core/portal_view`) shows the destination of portals on **OpenGL and Vulkan** (same
  screenshots on both), for portals into other dimensions and into the same dimension.
  Phase 6 is in progress: one portal layer only, no nested portals, no mirrors.
* Phase 7: Sodium 0.9.2 works (client test on OpenGL and Vulkan with Sodium), with one limitation: no
  same-dimension portal views (see "Sodium"). Iris 1.11.6 works without and with shader packs; tested with
  Complementary Shaders Reimagined and Unbound r5.9.3 (see "Iris").
  Portal shapes, portal rotations with roll and a camera right in front of a portal are handled
  (see "Polish pass").
* Not yet observed: the real dedicated server (`runServer`, needs `eula=true`, see blockers).

## Decisions that differ from the original plan

* **Loom 1.17.21 instead of 1.17-SNAPSHOT / 1.17.9.** 1.17.21 is the newest stable
  1.17 release on maven.fabricmc.net (checked 2026-09-26).
* **DimLib is a Gradle subproject (`:dimlib`), not copied into the main source tree.**
  It keeps mod id `dimlib`, its entrypoints, mixin config and Apache-2.0 license, and is
  nested into the jar with `include`. See `dimlib/PORTING.md`.
* **Publishing plugin removed.** `me.modmuss50.mod-publish-plugin` targeted the upstream
  CurseForge, Modrinth and GitHub projects. `maven-publish` stays, with no remote repository.
* **Gravity Changer integration dropped at build level.** The mod has no 26.3 release and
  its repository is archived. The runtime no-op fallback in `GravityChangerInterface` stays.
* **Quarantined sources stay in the tree unchanged.** They are excluded from compilation in
  `build.gradle` (`portQuarantine`), and quarantined mixins are moved to configs that
  `fabric.mod.json` does not register. Restoring a feature means removing the exclusion.
  Code that the active sources still need from a quarantined area was ported in place
  (see `portQuarantineKeep`), with `PORT(26.3)` comments where behaviour was removed.
* **Player position dimension.** `ClientboundPlayerPositionPacket` became a record with a
  fixed stream codec, so the dimension can no longer be appended to it. The server sends
  `imm_ptl:player_position_dimension` (teleport id + dimension) right before every position
  packet; the client pairs them by teleport id (`ClientTeleportationManager
  .consumePositionPacketDimension`). Both are handled in order on the client packet
  processor (Fabric reschedules payloads through `Minecraft.packetProcessor()`).
* **Redirected packets** are rescheduled through `Minecraft.packetProcessor()` instead of
  `Minecraft.execute`, because 26.3 queues vanilla packets there; otherwise redirected and
  normal packets could be reordered.
* **Remote procedure calls** (amendment 5): reflection-by-name dispatch was replaced with an
  explicit allowlist (`ImplRemoteProcedureCall.registerServerbound/registerClientbound`,
  registrations in `ImmPtlRemoteCalls` and `PeripheralModMain`) and typed codecs. Unknown
  methods, malformed arguments and trailing bytes are rejected without throwing.
* **Portal wand overlay** is emitted as vanilla gizmos (`GizmoLineVertexConsumer`,
  `WireBuffers`) from `DebugRenderer.emitGizmos`, because immediate-mode
  `MultiBufferSource` line rendering no longer exists. The wire drawing code is unchanged.
* **Client worlds.** Every loaded dimension gets its own `LevelRenderer` and
  `LevelExtractor`; `ClientWorldLoader.withSwitchedWorld` and client dimension changes swap
  both. The sea level of non-player dimensions is not sent by the server, so vanilla values
  are used (nether 32, others 63).
* **`ImmPtlClientChunkMap`** keeps its own double-buffered added/removed chunk and empty
  section sets, because 26.3's section occlusion graph only learns about chunks through
  `ClientChunkCache.addedLoadedChunks()` and friends.
* **Global portal storage** is saved as `data/immersive_portals/global_portal.dat` per
  dimension (`SavedDataType`); the old `data/global_portal.dat` is migrated on load.
* **Portal helper block render layer** registration was removed: 26.3 derives the chunk
  layer from the sprite's transparency (`ChunkSectionLayer.byTransparency`).
* **World time** is no longer sent per dimension (`WorldInfoSender`): 26.3 world clocks are
  global and every client level receives `ClientboundSetTimePacket` game time.
* **Teleport request validation** (amendment 4): the rules are in `TeleportRequestCheck` and
  apply to mounted players too. Additionally rejected: non-finite positions, unknown dimension
  ids (previously an exception); a missing portal now also resyncs the client. Rejection logs
  are rate limited. The vehicle keeps travelling with its player as before (no separate
  vehicle permission check was added).
* **Game tests** live in a separate source set and test mod (`src/gametest`, mod id
  `immersive_portals_gametest`) that is not packaged. `fabric-gametest-api-v1` is only on
  that classpath. The GameTest server skips the EULA prompt by itself (Fabric API
  `MainMixin`); nothing writes `eula.txt`.
* **Mixins removed because 26.x vanilla does the same** (file deleted, config entry removed):
  * `MixinProjectile` (owner lookup in all dimensions): `EntityReference` uses `getEntityInAnyDimension`.
  * `MixinThrownEnderPearl` (cross-dimension pearl teleport): vanilla teleports the owner
    across dimensions through `TeleportTransition`.
  * `MixinLevel.onInitWeatherGradients` (nether rain fix): weather is only prepared for levels
    that `canHaveWeather()`.
  * `MixinBiomeAmbientSoundPlayer`: the handler reads `player.level()` every tick.
  * `MixinAbstractClientPlayer` / `IEAbstractClientPlayer`: the `clientLevel` field no longer exists.
* **Mixins rewritten for changed targets**:
  * `MixinChunkMap_C`: the `@Overwrite` of `onChunkReadyToSend` became a HEAD inject plus a
    `@WrapWithCondition` on `markChunkPendingToSend`, so vanilla's broadcast registration and
    debug sync keep running.
  * `MixinEntity`: inside-block checks run per movement step in 26.x; the portal-clipped
    collision box is applied to each step's box.
  * `MixinEntity_Interpolation` (new) replaces the `lerpTo` mixins of `LivingEntity` and
    `AbstractMinecart`: every entity interpolates through `moveOrInterpolateTo`.
  * `MixinTrackedEntity`: redirects moved to the `ServerEntity.Synchronizer` methods
    (`sendToTrackingPlayers[Filtered|AndSelf]`).
  * `MixinContainerOpenersCounter`: adds players using a container through a portal to
    `getEntitiesWithContainerOpen` instead of replacing the list.
  * `MixinParticleEngine` render hooks moved to `MixinParticleGroup` / `MixinQuadParticleGroup`.
  * Debug screen text: `MixinDebugScreenOverlay` replaced by a registered `DebugScreenEntry`
    (`immersive_portals:debug`, toggled in the debug options screen).
  * Retargeted: `MixinAbstractContainerMenu`/`MixinMultiPlayerGameMode` (lambda names),
    `MixinContainer`/`MixinServerPlayerGameMode` (`isWithinBlockInteractionRange`),
    `MixinGameRenderer_B` (`Minecraft.pick`), `MixinMinecraft_B` (`pickBlockOrEntity`),
    `MixinMinecraft` fps (`renderFrame`), `MixinItemEntity_P` (`EntityReference` thrower),
    `MixinCreateWorldScreenMoreTab_CVB` (`this$0`, `@Local` row helper),
    `MixinServerGamePacketListenerImpl_Redirect` (`ChannelFutureListener`).
* **Dimension types** `immersive_portals:surface_type[_bright]` were converted to the 26.3
  schema (based on the vanilla overworld type; 256 high from y 0, raids off, respawn anchors
  on). The old `ambient_light` 15 of the bright variant is now 1.0.

* **Per-frame client work** (`MixinMinecraft_Frame`): the head of the old `GameRenderer.render` hook
  (quarantined with the render mixins) did the per-frame teleport check, the partial tick in
  `RenderStates`, portal animations, `PRE_TOTAL_RENDER_TASK_LIST` and `PRE_GAME_RENDER_EVENT`. Without it
  the client only teleported on ticks, and `RenderStates.getPartialTick()` stayed 0 during frames. It now
  runs in `Minecraft.renderFrame` right before `GameRenderer.update` (the camera update), together with
  `PortalRenderer.switchToCorrectRenderer` (which had no caller either). The same hook
  runs `ClientLevel.update()` for the other client worlds: vanilla only does it for the player's level,
  and without it their light engines never publish new light data (`LightEngine.runLightUpdates` swaps
  the visible section map). This replaces the old `MyRenderHelper.lateUpdateLight` (same debug switch,
  `IPCGlobal.lateClientLightUpdate`).
* **Window resize** (`MixinGameRenderer_MultiWorld`) resizes the other dimensions' level renderers
  (entity outline target, occlusion graph), as the quarantined render mixin did.

## Portal rendering prototype (phase 5)

Design (all through the renderpearl GPU abstraction, no GL calls, no stencil):

* Extraction: after `GameRenderer.extract` extracted the main level, every visible portal into
  another dimension (at most 2, nearest first) is extracted by the destination's own
  `LevelExtractor` with a `PortalViewCamera` (the main camera transformed by the portal) into a
  `LevelRenderState` owned by the view. The extractor's and renderer's state fields are swapped
  for this (`LevelExtractorAccessor`, `LevelRendererAccessor`).
* Clipping: the world between the transformed camera and the destination plane is removed with an
  oblique near plane in the view's projection matrix (`ObliqueClipping`, unit tested for regular
  and reversed depth with both clip depth ranges; 26.3 uses reversed depth).
* Drawing: after `GameRenderer.renderLevel` drew the main level, the destination's
  `LevelRenderer` draws each view into an offscreen `TextureTarget` (by temporarily swapping
  `GameRenderer.mainRenderTarget`). Each view has its own projection, fog and global uniform
  buffers so the main frame's buffers are never rewritten mid-frame. Then the portal quad is drawn
  into the main target with the `immersive_portals:pipeline/portal_view` pipeline, which samples
  the view in screen space (`projection_from_position` + `textureProj`, like the end portal),
  depth tested and depth writing.
* `MixinSkyRenderer`: `LevelRenderer` creates its `SkyRenderer` lazily with the then-current
  render target; a level first drawn inside a portal view would keep drawing its sky into the view
  target, so the sky now always uses the current target.

Verified by the client game test: screenshot through the portal shows the nether test room (gold
wall and glowstone floor, the obsidian wall behind the destination point clipped) on OpenGL
(AMD 26.8.1) and Vulkan 1.4.315 (AMD); `PortalViewRenderer.getViewCountThisFrame() == 1`.

* Same-dimension portals reuse the level's own `LevelRenderer`/`LevelExtractor` with a second
  camera in the same frame (no second copy of the chunk meshes). The view's extraction must not
  consume the chunk-cache deltas that the main render state still holds, so
  `ImmPtlClientChunkMap.withoutTrackingSetConsumption` hands out empty deltas meanwhile. Verified
  in the client test: emerald wall at the destination visible, red wool behind the destination
  point clipped, main view unchanged 20 ticks later and after turning away. Cost: the level's
  occlusion graph is recomputed for two cameras per frame.

### Polish pass

* The portal area is the portal's own view-area mesh (`Portal.renderViewAreaMesh`: rectangular and
  special shapes, global portals), not a rectangle.
* Camera right in front of a portal: the portal area is cut at the camera and projected along the view
  rays onto a plane just beyond the near plane (`PortalAreaMesh`, unit tested), within 0.3 blocks of the
  portal. Before, the near plane cut the portal away and the world behind it showed. The client test
  checks a pixel with the eye 0.03 blocks in front of the portal; with the projection disabled that check
  fails (the overworld sky is visible).
* The destination camera uses the full rotation (main camera rotation times the portal rotation), so a
  portal rotation that rolls the view is drawn correctly (client test screenshot 07, OpenGL and Vulkan).
* Mirrors are skipped: a reflection is not a camera rotation and flips face culling (phase 6).
* The oblique clip plane is kept at least 0.005 blocks away from the destination camera.
* The clouds' uniform ring buffer is rotated before every portal view draw. It is written by every
  `LevelRenderer.render` call and vanilla rotates it once per frame for the player's renderer only; on
  Vulkan, a same-dimension view would otherwise overwrite the cloud data of the main view before the
  frame is submitted. The ring buffer is fenced, so the extra rotations are safe.
* 26.3 applies view bobbing only to the hand, so no bobbing correction is needed for portal views.

Not done (phase 6): nested portals, mirrors, fuse-view portals (drawn like normal portals, with sky),
portal frame/overlay rendering, performance (every view re-extracts every frame).

## Sodium (phase 7)

Sodium gives every `LevelRenderer` its own `SodiumWorldRenderer`, so every client world keeps its own
chunk meshes. The compat layer (`SodiumInterface`, `SodiumInterfaceOnPresent`) only uses Sodium classes
directly; it needs no mixins into Sodium:

* Chunk tracking: `ImmPtlClientChunkMap` replaces the `ClientChunkCache` methods that Sodium hooks, so it
  reports loaded and dropped chunks to Sodium's `ChunkTrackerHolder` itself (light data still arrives through
  Sodium's own packet listener hook, which works for redirected packets).
* Sodium's `LevelExtractor` hooks (`setLevel`, `setSectionDirty`, ...) act on the terrain renderer of the
  current `Minecraft.levelRenderer`. `ClientWorldLoader` created and disposed other dimensions' extractors
  with the player's level renderer current, which would have bound the player's Sodium renderer to the new
  dimension. Those calls and `ImmPtlClientChunkMap.onLightUpdate` now run with the dimension's own level
  renderer current (`ClientWorldLoader.withLevelRendererCurrent`).
* Sodium draws terrain with the projection it captures in `GameRenderer.renderLevel`; a portal view sets it to
  the view's (obliquely clipped) projection while it draws (`SodiumInterface.swapTerrainProjection`).
* Sodium sets up the terrain with the fog of `GameRenderer.fogRenderer`; a view swaps in its own fog renderer
  during its extraction.
* A view's camera state and fog are now set up before the level extraction, like `GameRenderer.extract`
  does for the main view (before, the section occlusion graph used the previous frame's view camera), and
  views use frustum culling only (the destination camera can be inside terrain behind the destination plane).

Limitation: a Sodium renderer keeps the culling results (render lists, one `ChunkRenderList` per region),
cached draw batches and chunk uniforms (written once per frame) of the last camera that set it up. So with
Sodium, each level renderer is used by one camera per frame: portals into the player's own dimension, and a
second view into a dimension that already has one in the frame, are not drawn (logged once). The old
compatibility layer swapped Sodium's render lists per portal and needed mixins into Sodium internals for that.

The old Sodium mixins (`compat/mixin/sodium/*`) and `SodiumRenderingContext` / `IESodiumRenderSectionManager`
were removed. They served the stencil renderer: clip planes injected into Sodium's shaders (replaced by the
oblique projection), per-portal-layer render lists and render-list swapping (replaced by one camera per
renderer and frame), an occlusion-culling start point at the portal (replaced by frustum culling for views),
section culling by the portal's frustum (not ported; a performance optimization) and the forced main-thread
rebuild (quarantined with the old renderer).

Verified: `runClientGametest -Penable_sodium=true` on OpenGL and Vulkan (all checks pass, including both pixel
checks through the nether portal; the same-dimension view is asserted not drawn with Sodium), and the
normal (vanilla) run.

## Iris (phase 7)

`IrisInterfaceOnPresent` uses Iris' API (`IrisApi.isRenderingShadowPass`) and `Iris.getCurrentPack` /
`getCurrentPackName`; no mixins into Iris. `IrisInterface` lost `getPipeline`, `setPipeline` and
`reloadPipelines`: they swapped the pipeline field that Iris adds to `LevelRenderer` for the old renderer, and
Iris 1.11.6 prepares the pipeline in every `LevelRenderer.render` from the current dimension anyway.

With a shader pack, Iris renders a level through the pipeline of `Iris.getCurrentDimension()` (from
`Minecraft.level`): its own G-buffers, a shadow pass, composite passes, and a final pass into
`GameRenderer.mainRenderTarget()`. Its uniforms (camera position, sun, sky colour, fluid) and the shadow pass take
the camera from `GameRenderer.mainCamera()`. A portal view draws the destination with the destination's level
renderer inside `ClientWorldLoader.withSwitchedWorld` and with its own target as `mainRenderTarget`, so Iris
already picks the destination dimension's pipeline and writes its final image into the view. In addition:

* `GameRenderer.mainCamera` is set to the view's camera while the view is drawn (`GameRendererAccessor`).
  Vanilla does not read it while drawing a level; Iris then computes its uniforms and the shadow map for the
  view. Views are drawn after the main level, so the main frame is not affected.
* The view camera counts as detached, so Iris does not draw the player's hand into the view (and a
  same-dimension view shows the player's body like other entities).
* The view camera's environment attribute probe (sky colour, sun angle, fog colours; 26.x) is now ticked once per
  client tick with the destination level and the view position. It was never ticked, so views used the
  attributes' default values; with Iris this showed as a dusk-coloured sky in the overworld seen from the
  nether. This also corrects sky and fog colours of views without shaders.
* Iris keeps a pipeline per dimension. With Sodium (which Iris requires) a level renderer only draws one camera
  per frame, so each pipeline renders either the main view or one portal view per frame and its per-frame state
  (frame counter, previous-frame matrices for TAA) belongs to that camera.

Verified with `IrisShaderPackTests` (client game test, skipped without Iris), for a minimal test pack and for
every `Complementary*.zip` in `build/clientgametest/shaderpacks/` (Complementary Shaders Reimagined r5.9.3 and
Unbound r5.9.3 from Modrinth, sha512 checked; downloaded with the repository owner's permission and not
committed). For each Complementary pack: the gold wall of the nether room is visible in the portal (pixel check),
also with the eye 0.03 blocks in front of the portal; a stone block between player and portal hides the portal
(pixel check; the main target's depth is valid after Iris' final pass); walking through the portal reaches the
nether; the overworld is drawn through a portal in the nether, with sky, clouds and the shadow of a pillar
(screenshots checked).

Known limitations with shader packs:

* Each portal view runs the complete shader pipeline (shadow pass, G-buffers, composites) again, which costs
  about as much as the main view.
* The view uses the oblique projection for clipping; Iris passes it to the pack as `gbufferProjection`. Effects
  that assume a standard projection (depth linearization with `near`/`far`) may be slightly off in views; not
  seen in the tests.
* Temporal effects (TAA, motion blur) were only checked with a still camera.
* Not tested: other shader packs, Iris on the Vulkan backend.
* `IrisTimeUniforms` (frame time) is updated by every `LevelRenderer.render` call, so it advances twice per frame
  while a view is drawn.

## Dedicated server

`DedicatedServerPortalTests` (client game test) starts an in-process dedicated server, connects the client
over a real connection and goes through a portal into the nether and back. Dedicated servers only start
after the Minecraft EULA is accepted, which is up to whoever runs the tests: the test is skipped (logged
"SKIPPED DedicatedServerPortalTests") unless `build/clientgametest/eula.txt` contains `eula=true`. The real
`runServer` (server-only classpath) likewise needs `run/eula.txt`. Neither has been run yet.

## Known issues

* Portal views are drawn after the whole level, including translucent blocks, particles and weather.
  Translucent things between the camera and a portal (glass, water, particles) are hidden by the portal
  area. The old renderer drew portals before the translucent pass.
* `IPModInfoChecking` requests the upstream mod info on startup. There is none for 26.3 (HTTP 404); this
  is now logged once at INFO level instead of as an error.

Fixed in the polish pass:

* "Chunk loading failure" (1-2 per client test run): `ImmPtlChunkTickets` checked the entity-ticking
  future of a chunk whose new ticket had not been applied yet (tickets are applied in
  `DistanceManager.runAllUpdates`), saw vanilla's completed "unloaded" placeholder and freed the
  throttling slot at once. Such chunks now keep waiting; a chunk that is not entity-ticking after 30
  seconds frees its slot with a warning. 0 occurrences in the following client and server runs.
* A failed client game test no longer hangs: Fabric Loader showed its error window and waited for it
  to be closed. `runClientGametest` passes `-Dfabric.noGui=true`; a forced failure ended the run in
  36 s with BUILD FAILED.
